## 1. Deliveries Page: Add Clear Actions for Returns, Reconciliation, Details, Reversal, and Reloading

The Deliveries page currently shows tabs such as:

* Active Loads
* Returns
* Reconciled
* Setup

The issue is that the Returns tab shows many return records, but there is no clear action to reconcile, approve, view, or manage them.

### Required changes

On the Returns tab, add an Actions column.

Each return row should clearly show available actions based on status.

For return records that are not yet reconciled, show:

* View Details
* Reconcile / Approve
* Edit Return, if the return has been saved but not reconciled

* View Details
* Reverse Reconciliation

* View Details
* Reverse Reconciliation

## 3. Add Reverse Reconciliation Support

Once a delivery has been reconciled, the user currently cannot edit or reverse it.

Add the ability to reverse reconciliation so mistakes can be corrected.

### Required behavior

When the user clicks `Reverse Reconciliation`, show a confirmation modal:

“Are you sure you want to reverse this reconciliation? This will undo the linked sales, payments, inventory movements, customer balance updates, and shortage/overage records created by this reconciliation. You can then edit and reconcile the delivery again.”

The user must enter a reason for reversal.

### Reversal should safely undo or mark inactive:

* Sales records created from the delivery reconciliation
* Sale items created from the delivery reconciliation
* Payment records created from the delivery reconciliation
* Customer balance impacts from credit sales
* Inventory movements for sold, returned, and damaged goods
* Shortage/overage records
* Any linked delivery expense records, if applicable

Preferred approach:

Do not physically delete records if the system already supports status/inactive flags. Instead, mark linked records as reversed/inactive and create reversal audit records.

All linked records should be traceable using:

* SourceType = DeliveryRun
* SourceId = DeliveryRunId

After reversal:

* Delivery status should move back to a state that allows editing and reconciliation again.
* Example status: `ReturnedPendingReconciliation` or `Loaded`, depending on where the workflow should resume.
* The user should be able to edit the return and reconcile again.

Avoid duplicate records when the delivery is reconciled again.

## 12. Daily Closing: Allow Reopen/Resubmit Closing for a Day

The Closing page needs the ability to resubmit closing for a given day.

Business reason:
A user may close a day, then later discover that additional sales, expenses, production, delivery returns, or losses were entered or corrected. The user must be able to reopen or resubmit the closing so the final daily summary reflects the corrected data.

### Required behavior

For a submitted daily closing, add an action:

* View Details
* Reopen / Undo Closing
* Resubmit Closing

Preferred workflow:

When user clicks Reopen/Undo Closing:

* Require a reason.
* Mark the existing closing as Inactive, Reopened, or Superseded.
* Do not physically delete the old closing.
* Allow the user to generate and submit a new closing for the same date.

The new closing should become the active closing for that day.

The old closing should remain in history for audit purposes.

Closing records should support:

* ClosingDate
* Status: Submitted, Reopened, Superseded, Active, Inactive, etc.
* IsActive
* SupersededByClosingId
* ReopenedBy
* ReopenedAt
* ReopenReason
* SubmittedBy
* SubmittedAt

Only one closing should be active for a given company and closing date.

The closing details should show whether it replaced a previous closing.
